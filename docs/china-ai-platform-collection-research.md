## 一、背景与动机

### 1.1 为什么要做这件事

AnswerX GEO 是面向出海品牌的 AI 搜索引擎优化 SaaS 平台。平台的核心能力是监测品牌在 AI 搜索引擎中的可见度、引用情况和情感倾向，帮助品牌在"问 AI"时代获得更多曝光。

**目前的监测范围：** 美国 AI 平台——ChatGPT、Gemini、AI Mode、Perplexity，通过第三方代理服务 Cloro 实现数据采集。

**Cloro 的工作方式：**
- 异步 API 调用：`POST /v1/async/task` 提交采集任务
- Webhook 回调：Cloro 完成采集后回调通知
- PubSub 入库：回调数据经 Google Cloud PubSub 写入 Cloud SQL
- Strategy Pattern：支持多平台解析的策略模式架构

**现在的需求：** 扩展到中国市场，监测中国主流 AI 平台的品牌可见性。

### 1.2 核心问题：中国没有 Cloro

经过深入调研，核心结论是：**不存在等价于 Cloro 的中国 AI 平台代理服务。**

**Cloro 本身的覆盖范围：**
- 支持：ChatGPT, Perplexity, Copilot, Google AI Mode, Google Search, Gemini

- 其他中国平台（豆包、Kimi、文心一言、通义千问、元宝、秘塔）完全不支持

**西方 SERP API 的覆盖：**
- SerpApi、Bright Data、Oxylabs、Scrape.do 等主流 SERP API
- 没有任何一家支持爬取中国 AI 搜索 UI

**市场数据：**
- 中国 GEO 市场预计 2026 年达 **286 亿元**，同比增长 **60%+**
- **62.2%** 中国用户偏好"问 AI"而非传统搜索
- 这是一个**基础设施层的市场空白**——需求存在，但没有现成的工具可用

#### 核心发现：双模式采集架构

#### 浏览器插件技术深挖

**1. 任务分发：HTTP 轮询**
- 插件每 ~4 秒向后端 `/extension_monitor/status/` 发 GET 请求
- 返回内容：插件在线状态、自动接单开关、各平台登录状态
- 用户提交关键词检测任务（`execution_mode: 'extension'`）进入后端队列
- 插件下次轮询时领取任务

**2. 查询注入：Content Script + DOM 操作**
- 检测用户是否已登录各 AI 平台（检查 session cookies）
- 打开新标签页到目标 AI 平台聊天界面
- Content script 注入查询文本到输入框，模拟点击发送

**3. 响应捕获：MutationObserver**
- 监听 AI 回答区域 DOM 变化
- 等待 DOM 停止变化（回答生成完毕）
- 提取最终文本，回传后端
- 还能测量 TTFT（Time-to-First-Token）

**4. 执行模式：严格串行**
- 一次只能查一个平台，代码明确单选
- 100 prompt x 7 平台 = 串行提交 7 个独立任务

**5. "自动接单"模式**
- 开关控制，开启后自动从队列领取并执行任务
- 关闭则空闲

### 2.3 我们能借鉴什么

1. **HTTP 轮询 + 任务队列模式** —— 简单可靠，无需 WebSocket 长连接
2. **Content script 注入 + MutationObserver 捕获** —— 浏览器扩展的标准技术栈
3. **"自动接单"开关** —— 好的用户体验设计
4. **各平台登录态检测** —— 在执行前验证可用性
5. **接入码/多后端设计** —— 可扩展的白标架构
6. **双模式（插件 + 云端）架构** —— 互补的采集策略

### 2.4 我们能做得更好的

1. **并行执行** —— 超算GEO 严格串行（一次一个平台），我们可以同时开 3-5 个标签页对应不同平台并行采集，吞吐量提升 3-5 倍
2. **与现有 Cloud SQL 直接对接** —— 数据直接进入已有的数据管道
3. **更丰富的元数据提取** —— 不只是纯文本，还有 citations、sources、链接等结构化数据

## 三、基础概念详解

> 本章面向非技术读者，解释后续方案中涉及的核心技术概念。

### 3.1 爬取 (Scraping/Crawling)

用程序自动访问网页、提取数据。就像用浏览器打开网页复制文字，但用代码自动完成。

### 3.2 浏览器自动化 (Browser Automation)

用代码控制一个真实的浏览器（Chrome），让它像真人一样操作——打开网页、点击按钮、输入文字、等待加载、读取结果。

**为什么需要浏览器自动化？** 因为现代 AI 平台是动态网页应用：
- 内容通过 JavaScript 渲染
- 回答流式生成（逐字出现）
- 不能简单发 HTTP GET 请求获取内容

必须完整模拟浏览器行为：**打开浏览器 → 登录 → 输入问题 → 等 AI 回答完 → 提取结果。**

### 3.3 Playwright

Microsoft 开发的开源浏览器自动化框架，支持 Python/JS/Java/C#。**目前最主流的浏览器自动化方案。**

Playwright 脚本 = 用 Playwright 框架写的 Python 代码，告诉浏览器该做什么。

**具体示例——采集 DeepSeek 的回答：**

```python
from playwright.async_api import async_playwright

async def query_deepseek(question: str):
    async with async_playwright() as p:
        # 启动 Chrome 浏览器（无头模式，不显示窗口）
        browser = await p.chromium.launch(headless=True)
        
        # 创建浏览器上下文，配置代理
        context = await browser.new_context(
            proxy={"server": "http://proxy.kuaidaili.com:15818",
                   "username": "...", "password": "..."}
        )
        
        # 加载已保存的登录 cookies
        await context.add_cookies(saved_cookies)
        
        # 打开 DeepSeek 页面
        page = await context.new_page()
        await page.goto("https://chat.deepseek.com")
        
        # 输入问题
        await page.fill("textarea", question)
        
        # 点击发送
        await page.click("button[type='submit']")
        
        # 等待回答生成完毕（停止按钮消失 = 回答完成）
        await page.wait_for_selector(".stop-button", state="hidden", timeout=60000)
        
        # 提取回答文本
        answer = await page.inner_text(".answer-container")
        return answer
```

**其他类似框架：**
- **Puppeteer**（Google 开发，只支持 Chrome + JavaScript）
- **Selenium**（更老更慢，兼容性差）
- **结论：Playwright 是最佳选择**

### 3.4 代理 (Proxy)

请求的"中转站"。

- **没有代理时：** 你的服务器 IP 直接暴露给 AI 平台，大量请求会被封禁
- **有代理时：** 请求通过不同的家庭/手机 IP 发出，AI 平台看到的是普通用户

**代理和 Playwright 的关系：**
- **Playwright** = 操作浏览器的手（控制做什么）
- **代理** = 浏览器的面具（让浏览器看起来来自不同地方）
- 两者配合使用

### 3.5 住宅代理 (Residential Proxy)

使用真实家庭宽带 IP 的代理。相比数据中心 IP，住宅 IP 更难被检测为机器人。

国内代理商（快代理、站大爷）收集大量中国家庭/手机 IP，以 API 形式出售。每次请求走不同的家庭 IP，AI 平台几乎无法区分你和真实用户。

### 3.6 反检测 (Anti-Detection)

AI 平台会检测你是不是机器人。反检测就是让自动化浏览器看起来像真人。

**检测方式与对策：**

| 检测方式 | 原理 | 难度 |
|---------|------|------|
| IP 信誉 | 服务器/数据中心 IP 直接标记 | 用住宅代理解决 ✅ |
| navigator.webdriver | 自动化浏览器标记为 true | stealth 插件修复 ✅ |
| 浏览器指纹 | Canvas/WebGL/字体渲染模式 | stealth 插件部分修复 ⚠️ |
| TLS 指纹 | 加密握手特征不匹配 | 很难修复 ❌ |
| 行为分析 | 鼠标/点击/滚动模式太"完美" | 需要模拟随机行为 ⚠️ |
| 频率限制 | 同一账号/IP 短时间大量请求 | 分散请求+多账号 ✅ |

**playwright-stealth** 插件能自动修复前 3 项，但 TLS 指纹和深度行为分析仍是挑战。

### 3.7 云浏览器 (Cloud Browser / Scraping Browser)

云端运行的 Chrome 浏览器，你通过 WebSocket/CDP 远程控制。

**类比：** 浏览器跑在别人的服务器上，你只发遥控指令。

**代码差异就一行：**

```python
# 本地浏览器（方案 A）
browser = await playwright.chromium.launch()

# 云端浏览器（方案 B/C）
browser = await playwright.chromium.connect_over_cdp("wss://云浏览器地址")

# 后续代码完全一样
```

### 3.8 Browser Context

一个浏览器进程内的独立"标签组"。每个 context 有独立的 cookies、localStorage、代理设置。

**关键优势：** 比启动多个独立浏览器实例轻量 **5-10 倍**。这是并发的关键优化——一个浏览器进程可以开 50 个 context 并行采集。

### 3.9 VPS vs Cloud Run vs GCE

| 概念 | 说明 | 计费 | 适合 |
|------|------|------|------|
| **VPS** (Virtual Private Server) | 虚拟专用服务器，GCP 语境下就是 GCE | 固定月付 | 持久进程 |
| **Cloud Run** | 无状态 serverless，容器随时可能被回收 | 按请求计费 | 轻量 API |
| **GCE** (Compute Engine) | 常驻虚拟机，完全控制 | 固定月付 | 重计算 |

**为什么跑 Chrome 适合 GCE 不适合 Cloud Run：**
- Chrome 需要持久进程和大量内存
- 一个 AI 回答要等 10-30 秒
- Cloud Run 等待期间也在计费，不划算
- Cloud Run 容器随时回收，登录状态会丢失

**但 Cloud Run 适合发 WebSocket 指令：** 方案 B/C 中，脚本只发遥控指令（轻量），浏览器在别人服务器上跑。

### 3.10 CDP (Chrome DevTools Protocol)

Chrome 浏览器暴露的调试协议。Playwright 通过 CDP 控制浏览器。

远程浏览器通过 WebSocket 暴露 CDP 端点，Playwright 连接即可远程控制——这就是云浏览器方案的技术基础。

## 四、总体方案：双轨并行

我们采用两条并行的采集路线：

### 路线一：浏览器插件采集

- **实现方式：** Chrome Extension，利用客户/我们自己的真实浏览器 session
- **反检测风险：** 零——用户的真实浏览器，AI 平台无法区分自动化和手动操作
- **适合场景：** 小规模、客户自助、合规敏感场景

### 路线二：云端/服务端采集

- **实现方式：** 服务端自动化，无需人工保持浏览器开着
- **适合场景：** 大规模、定时批量、高频监测

**云端采集有三种实现方案（A/B/C），方案只确定架构模式，不耦合供应商。** 供应商在第七章独立分析。

## 五、云端采集三种方案详解

### 方案 A：纯自建

**架构图：**

```
┌──────────────────────────────────────────────────────┐
│  GCE 虚拟机 (16-32GB RAM)                             │
│  ├── Playwright 脚本 (Python)                         │
│  ├── Chrome 浏览器进程（多个 Browser Context）          │
│  ├── playwright-stealth 反检测                        │
│  ├── asyncio 并发池                                   │
│  └── 通过代理商 API 获取住宅 IP                         │
│       └── 代理商（快代理/站大爷/蜻蜓代理）               │
│            └── 中国 AI 平台                            │
└──────────────────────────────────────────────────────┘
```

**你需要管理的：**
1. GCE 虚拟机（开机、监控、安全补丁、磁盘）
2. Chrome/Chromium 安装和版本更新
3. 浏览器进程监控（Chrome 会崩溃、内存泄漏、僵死，需要 watchdog 自动重启）
4. 并发控制（semaphore + 队列）
5. 扩容时手动加机器或配置 GKE autoscaling
6. Playwright 脚本开发和维护
7. 代理商 API 对接

**Playwright 脚本跑在：** GCE 虚拟机上（和浏览器同一台机器）

**为什么不能用 Cloud Run：**
- Cloud Run 无状态，容器随时回收
- Chrome 需要持久进程，登录状态要保持
- 一个 AI 回答要等 10-30 秒，100 个 prompt 跑 30+ 分钟
- Cloud Run 计费模式不适合：等待 AI 回答的空闲时间也在计费

**也可以考虑 Cloud Run Jobs：** 最长可跑 24 小时，适合批处理。但每次 job 启动要重新加载 cookies、启动浏览器，有 3-5 秒冷启动。

### 方案 B：云浏览器方案

**架构图：**

```
┌──────────────────────────────────────────────────────┐
│  Cloud Run (geo_collector 模块)                       │
│  ├── Playwright 脚本 (Python)（轻量，只发 WebSocket 指令）│
│  └── WebSocket 连接                                   │
│       └── 云浏览器供应商的服务器                         │
│            ├── Chrome 浏览器进程（供应商管理）            │
│            ├── 反检测（供应商内置）                       │
│            └── 通过代理商 API 获取住宅 IP               │
│                 └── 代理商（快代理/站大爷/蜻蜓代理）      │
│                      └── 中国 AI 平台                  │
└──────────────────────────────────────────────────────┘
```

**你需要管理的：**
1. Playwright 脚本开发和维护
2. 代理商 API 对接
3. Cloud Run 部署（已有 Tech Stack）

**你不需要管理的：**
- 浏览器进程 / 服务器 / 运维 / 崩溃恢复 / 版本更新 / 并发管理

**Playwright 脚本跑在：** Cloud Run（现有 geo_collector 模块），完全融入现有 Tech Stack。

**关键区别：** 浏览器和脚本解耦。脚本是"遥控器"（轻量），浏览器是"电视"（重资源，供应商扛）。

```python
# 连接云浏览器——就改这一行
browser = await playwright.chromium.connect_over_cdp(
    "wss://less.nstbrowser.io/connect?token=xxx"
)

### 方案 C：全托管

**架构图：**

```
┌──────────────────────────────────────────────────────┐
│  Cloud Run (geo_collector 模块)                       │
│  ├── Playwright 脚本 (Python)（轻量，只发 WebSocket 指令）│
│  └── WebSocket 连接                                   │

│            ├── 代理 IP（供应商内置，不需要另找代理商）     │
│            └── CAPTCHA 解决（供应商内置）                │
│                 └── 中国 AI 平台                       │
└──────────────────────────────────────────────────────┘

**你需要管理的：**
1. Playwright 脚本开发和维护
2. Cloud Run 部署

**你不需要管理的：**
- 浏览器 / 服务器 / 代理 / 反检测 / CAPTCHA

**Playwright 脚本跑在：** Cloud Run（同方案 B）。

**关键区别（vs 方案 B）：** 方案 B 云浏览器和代理分开选。方案 C 全打包，一个供应商解决所有。

**方案 C 的限制：** 不能用自己选的代理商。如果全托管供应商的中国 IP 不够好，没有退路。

### 6.2 吞吐量评估

**单次采集耗时：**

| 环节 | 耗时 |
|------|------|
| 打开/切换标签页 | 1-3 秒 |
| 输入 prompt | 0.5-1 秒 |
| 等 AI 生成完整回答 | 10-30 秒（主要瓶颈） |
| 提取回答、回传后端 | 1-2 秒 |
| **单次总计** | **~15-35 秒** |

**各场景评估：**

| 场景 | 超算GEO（串行） | 我们的改进（并行） | 适合？ |
|------|---------------|-----------------|--------|
| 100 prompt x 1 平台 | ~50 分钟 | ~50 分钟 | ✅ 完全可行 |
| 100 prompt x 5 平台 | ~250 分钟 | ~50-70 分钟 | ✅ 完全可行 |
| 50 prompt x 7 平台 | ~175 分钟 | ~35-50 分钟 | ✅ 完全可行 |
| 500 prompt x 5 平台 | ~12.5 小时 | ~4-5 小时 | ⚠️ 勉强 |
| 1000+ prompt x 5 平台 | 不现实 | 8+ 小时 | ❌ 需要云端 |

**并行化是关键改进：** 同时开 5 个标签页对应 5 个平台，5 平台 x 100 prompt 和 1 平台 x 100 prompt 耗时基本一样。

**插件模式适合：** 每天几百条级别。AnswerX 早期（几个客户、每客户几十个关键词）完全够用。

## 十、风险与合规分析

### 10.1 法律合规风险

- **《数据安全法》《个人信息保护法》** 对自动化数据采集有限制
- 各 AI 平台 ToS 明确禁止自动化访问
- 公开的 API 服务（如"帮你爬豆包"）是显眼的靶子
- 内部工具灰色空间更大
- **超算GEO 的策略：** 包装成"SaaS 服务"而非"API 产品"，降低合规风险

### 10.2 技术风险

| 风险 | 说明 |
|------|------|
| **反检测军备竞赛** | SafeLine 等 WAF 在快速进化，stealth 插件有效期有限 |
| **TLS 指纹** | 目前 Playwright 无法完美模拟真实 Chrome 的 TLS 特征，需持续关注 |
| **账号瓶颈** | 中国 AI 平台要求手机号注册，批量注册是灰色地带 |
| **平台 UI 变更** | AI 平台经常更新前端，Content Script 的 DOM 选择器需要持续维护 |

### 10.3 供应商风险

| 风险 | 缓解措施 |
|------|---------|
| **国内代理商无正式 SLA**（快代理/站大爷都没有企业级 SLA，无财务补偿） | 双供应商 fallback |
| **单点故障**（只用一家代理商，挂了就全停） | 建议双供应商 fallback |
| **云浏览器供应商稳定性未知**（Nstbrowser 2023 年才成立，Scrapeless 更新） | 浏览器插件作为"安全阀" |
| **缓解措施** | 浏览器插件作为"安全阀"——即使云端采集全挂，插件模式仍可工作 |

### 10.4 关键瓶颈：中国手机号验证

所有中国 AI 平台都要求中国手机号注册。这不是技术问题，是**账号获取问题**。决定了能跑多少并行 session。

## 十一、方案建议

### 11.1 浏览器插件方案：确定要做，优先级高

**理由：**
1. **零反检测风险** —— 用户真实 session
2. **零运营成本** —— 不需要任何供应商
3. **合规风险最低** —— 等同于用户手动操作
4. **AnswerX 早期客户规模下完全够用** —— 几个客户 x 几十关键词
5. **开发周期短** —— 10-16 天
6. **作为云端采集的"安全阀"** —— 云端挂了还有 Plan B

### 11.2 云端采集方案：推荐方案 B1（Nstbrowser + 国内代理）

**首选 B1，理由：**
1. 不需要管浏览器运维
2. Playwright 脚本写在 Cloud Run 的 geo_collector 里，完全融入现有 Tech Stack
3. 月费最低（~$110）
4. 中国团队做的，支持 Playwright CDP
5. 代理可以灵活选择（快代理主、站大爷备）

**备选 C（Scrapeless 全托管）：**
- 如果 Scrapeless 定价合理，且中国 IP 质量好
- 最省心，但锁定供应商

**方案 A 作为 fallback：**
- 如果 Nstbrowser/Scrapeless 不稳定，退回自建 GCE
- 代码几乎不用改，只改浏览器连接方式

## 十二、为什么中国没有 Cloro？

### 12.1 市场需求还在形成期

中国 GEO 市场 2025 年才起步（比美国晚 1-2 年）。客户还在"我需要 GEO 服务"阶段，还没到"我需要 GEO 基础设施 API 自己搭"阶段。Cloro 的客户是开发者和 GEO SaaS——中国这个群体太小。

### 12.2 垂直整合文化

中国互联网更倾向垂直整合而非水平分层。美国有 Twilio、Stripe、Cloro 这种"卖铲子"传统。中国更倾向"全做"——智推时代宁可自建也不买第三方 API。

### 12.3 合规环境复杂

批量自动化访问 AI 平台涉及多个法律风险。公开的 API 服务是显眼靶子。内部工具灰色空间更大。这就是为什么超算GEO 把采集包装在 SaaS 里而非 API 产品里。

### 12.4 壁垒不高

Playwright + 代理 + stealth 对有经验的工程师不难。专门做 API 卖很难形成壁垒。有实力的公司都选择自建。

### 12.5 对我们意味着什么

如果做"中国版 Cloro"，窗口期存在但需要差异化：

- **不是**单纯卖代理 API（壁垒太低）
- **而是**卖"结构化 AI 平台数据"——标准化 JSON（品牌提及、citations、sentiment、sources）
- **目标客户：** 海外 GEO SaaS 想进中国 + 出海品牌想监测国内 AI 平台
- **路径：** 先作为自用基础设施，跑通后考虑是否对外开放

## 十三、总结与评估

### 13.1 核心结论

1. **中国没有 Cloro，这个市场空白是真实的**
2. **超算GEO 的双模式（插件+云端）架构是成熟方案，值得借鉴**
3. **浏览器插件是必做的、低风险的、高优先级的路线**
4. **云端采集推荐方案 B1（Nstbrowser + 国内代理），成本低、运维轻**
5. **供应商生态已经初步成熟，不需要从零造轮子**
