## 0. Context & 背景

### 0.1 问题源头
2026-04-09 Wentao 在 Lark 群中系统化反馈了 Analyze Agent 的三个结构性问题：
1. **报告可信度危机** — Roborock 行业 #1 被报告误判为表现不好；Agent 错误地把 perplexity/bing 归为 AI mode；建议行动里混入"知乎"这种不相关来源。
2. **模板体系定位不清** — 5 个分析模板不是同一维度（goal/domain/深度混杂），"趋势诊断"与"全面健康检查"语义重叠。
3. **RAFT 方法论误用** — RAFT (Readability/Answerability/Trustworthiness/Freshness) 是 Content 侧的评判标准，错误地出现在 Analysis 流程里。

相关文档：`docs/product_review_20260409.md`（Wentao 反馈全文 + 初步整理）。

### 0.2 根因分析（Phase 1 的诊断）

通过阅读 `geo_agent/src/pipelines/analysis_pipeline.py`（785 行），定位到报告不准确的**两个结构性 Hole**：

- **Hole A — Chart 数据从未进入 Synthesize Prompt**
  `step_synthesize_report`（line 629-684）在 line 639 读取了 `chart_results`，但只把它放进 `chart_results_final` 返回给前端，**从未拼接到 LLM 的 hydrated prompt 里**。LLM 合成报告时只能看到 Step 2 的 `variable_values`，所有图表计算出的数字它都看不见。
- **Hole B — Metric Discovery 是 LLM 自由发挥**
  `step_hydrate_metrics` (line 471) 调用 `_discover_metrics_for_prompt` (line 430)，让 Gemini 根据 prompt 文本和 live schema 自己"发明" variable_names。这些发明出来的变量名和模板 prompt 文本里的 `{{placeholder}}` 没有契约，匹配全靠 LLM 自觉，造成变量无法落位、LLM 只能凭记忆臆测。

此外反馈里隐含第三个结构性问题：

- **Hole C — 模板没有锁定"章节" / "指标"的 contract**
  同一个"全面健康检查"模板可能这次输出 3 章节、下次输出 2 章节；同一个"竞品对标"可能这次算 SOV、下次算引用率。缺一个模板级的 contract 确保 Agent 每次执行都覆盖同一组关键点。

### 0.3 已调研的代码现状（避免重复踩坑）

执行前已确认的关键事实：

| 事实 | 文件 / 证据 |
|---|---|
| `geo_analysis_metrics` 表曾在 migration 006 创建，migration 018 DROP 掉 | `migrations/018_drop_analysis_metrics.sql` |
| 当前 Agent 走"动态 schema 发现"模式（Hole B 的由来） | `analysis_pipeline.py:474` 注释 |
| `RECOMMENDED_CHARTS` 是前端硬编码 dict，DB 里 `config_type='recommended_chart'` 的行是死数据 | `TemplateConfigModal.tsx:181-204` |
| `inferredGoal` 用字符串匹配 template name，不是读 DB | `TemplateConfigModal.tsx:1962-1985` |
| `geo_agent_tasks.template_id` 是 **text** 列，无 FK 约束 | `Dump 3b` |
| `geo_agent_tasks` 只有 `analysis` 和 `content_generation` 两种 task_type | 用户确认 |
| 当前 Sidebar 已有 `FRAMEWORK > Metrics` 入口，但它是 RAFT 的 Content Framework Metrics（表 `geo_optimization_metrics`），不是 Analyzer 数据指标 | `Sidebar.jsx:43-48`, `MetricsPage.jsx` |

## 2. Phase 1 — 可信度修复（Credibility Fix）

### 2.1 目标
让 Analyze Agent 的产出报告**不再凭空造数**。在不引入任何新概念的前提下，把现有 pipeline 的数据流闭环补上。

### 2.2 具体修改清单

#### 2.2.1 Hole A — 把 Chart 数据注入 Synthesize Prompt

**文件**：`geo_agent/src/pipelines/analysis_pipeline.py`
**函数**：`step_synthesize_report` (line 629-684)

**改动**：
```
当前：
    hydrated = f"{prompt_text}\n\n## Computed Data (ground truth - do not fabricate)\n{data_section}"

改为：
    hydrated = f"{prompt_text}\n\n## Computed Data (ground truth - do not fabricate)\n{data_section}"
    hydrated += _format_chart_data_section(chart_results)
```

`_format_chart_data_section` 新建 helper，规则：
- 每张图产出一个 Markdown 表格，表头取 chart title + chart_type
- 行数限制：**全量输出，不截断**（Gemini Pro 1M context，tokens 消耗可控）
- 超过 500 行的图表保留 head 200 + tail 200，中间用 `...（省略 N 行）`
- 全部图表拼成一个 `## Chart Data` 章节附加到 prompt 末尾

#### 2.2.2 Hole B — Contract-Mode Metric Discovery

**文件**：`geo_agent/src/pipelines/analysis_pipeline.py`
**函数**：`step_hydrate_metrics` (line 471)

**改动**：增加契约模式分支
```
if template.wizard_config.required_metrics:
    metrics = [lookup_metric_registry(name) for name in required_metrics]
    # 对每个 metric 使用其 calculation_hint + relevant_tables 走 NL2SQL
else:
    metrics = await _discover_metrics_for_prompt(pool, prompt_text, domains, model_id)
    # 保留动态发现作为 Chat 入口 / 自定义分析 的 fallback
```

**注意**：Phase 1 实现时 `required_metrics` 来源于模板的 `wizard_config` JSONB 列。由于 Phase 1 不做 DB 变更，Phase 1 版本可以读一个**硬编码的 in-memory 映射表**作为 stub（模板 name → required_metrics 列表），Phase 2 再切到 DB。

硬编码 stub 放在 `geo_agent/src/pipelines/_template_contracts_stub.py`，Phase 2 上线时删除。

#### 2.2.3 Hole C — Template-Level Required Chapters

**文件**：`geo_agent/src/pipelines/analysis_pipeline.py`
**函数**：`step_quality_check`（已有）

**改动**：
- 从 stub（Phase 1）或 `wizard_config`（Phase 2）读 `required_chapters: string[]`
- 正则抽取 report markdown 的 H2 标题
- 缺失章节 → 返回 `status=failed_needs_retry` 触发重跑（最多 2 次），仍缺 → 最终报告标注"章节不完整"警告

#### 2.2.4 Synthesizer Prompt 约束强化

**文件**：`geo_agent/src/pipelines/analysis_pipeline.py`
**位置**：`step_synthesize_report` 的 system prompt

**新增约束**（追加到 system prompt 末尾）：
```
严格规则：
1. 所有数字、百分比、排名、趋势方向必须来自 "## Computed Data" 或 "## Chart Data" 章节。
2. 不允许引用这两个章节之外的任何数字。
3. 如果需要提及引用来源（citation source），只能使用 "## Chart Data" 中明确出现过的 source 名称；
   不允许引用"知乎""微博""小红书"等未在数据中出现的平台。
4. 分析 AI 平台时只能使用 [chatgpt, gemini, aimode] 这三个键；
   不允许把 perplexity、bing、claude 归为 "AI mode"。
```

#### 2.2.5 Evidence Chain 模块

**文件**：`geo_agent/src/pipelines/analysis_pipeline.py`
**位置**：`step_synthesize_report` 的 hydrated prompt 最前面

**新增章节**（放在 prompt 最前，让 LLM 先"看到"证据链再写报告）：
```
## 本次分析报告依赖的真实数据

执行的 SQL 查询数量：{n}
- Query 1: {table_name} | {时间窗口} | 聚合口径 | 返回行数
- Query 2: ...
- ...

后续的 "## Computed Data" 和 "## Chart Data" 就是这些 SQL 的执行结果。
```

这段文字本身也出现在最终报告的开头作为"数据依据"披露。

### 2.3 Phase 1 验收标准

用 Roborock 真实数据跑 5 次"全面健康检查"（即重命名后的"综合分析"）：
- ✅ 5 次报告都**正确识别 Roborock 为行业前列**，不再出现"表现不好"误判
- ✅ 5 次报告都**不出现 perplexity/bing 被归为 AI mode** 的错误
- ✅ 5 次报告都**不出现"知乎"等未在数据中出现的平台引用**
- ✅ 5 次报告都包含完整的 3 章节（visibility / citation / sentiment）
- ✅ 5 次报告的开头都有"本次分析报告依赖的真实数据"证据链披露
- ✅ 从报告里抽任意一个数字，都能在 Computed Data 或 Chart Data 中溯源

### 2.4 Phase 1 Migration 文件

**无**。Phase 1 是纯代码 patch，不动数据库。

## 3. Phase 2 — Template × Wizard 2D 配置 + Content 契约对等

### 3.1 目标
把 Phase 1 的 in-memory stub 升级为 DB-backed 的 Template × Wizard 2D 配置体系。让：
- 运营人员通过 Admin UI 配置 "每个模板允许用户看到的 wizard 步骤 + 默认值 + 数据/章节契约"
- Analyzer 和 Content 模板共享同一套 `wizard_config` JSONB 机制（task_type 区分 schema）
- Analyzer Metric Registry 独立管理（`geo_analysis_metrics` 表重建）
- 前端清理掉所有硬编码 dict 和字符串匹配

### 3.2 DB Schema 变更

#### 3.2.1 重建 `geo_analysis_metrics`

由于 migration 018 已经 DROP 过这张表，Phase 2 **重新创建**，schema 针对 NL2SQL agent 优化：

```sql
CREATE TABLE geo_analysis_metrics (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    metric_name TEXT NOT NULL UNIQUE,        -- 技术 key, e.g. 'visibility_rank_vs_peers'
    display_name_zh TEXT NOT NULL,            -- 中文展示名
    display_name_en TEXT,                     -- 英文展示名（可选）
    domain TEXT NOT NULL CHECK (domain IN ('visibility','citation','sentiment','custom')),
    description TEXT NOT NULL,                -- 业务含义
    calculation_hint TEXT NOT NULL,           -- 供 Agent NL2SQL 用的自然语言计算说明
    relevant_tables TEXT[] NOT NULL DEFAULT '{}',  -- Agent 优先查这些表
    sample_question TEXT,                     -- 示范 NL 提问
    null_behavior TEXT NOT NULL DEFAULT 'return_null'
        CHECK (null_behavior IN ('return_null','return_zero','raise')),
    unit TEXT,                                -- 展示单位, e.g. '%', 'count', '分'
    is_active BOOLEAN DEFAULT true,
    sort_order INTEGER DEFAULT 0,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

**与旧版（migration 006）的差异**：
- ✅ 去掉 `sql_override`（用户明确拒绝硬编码 SQL）
- ✅ 新增 `relevant_tables` 作为 Agent NL2SQL 的表级 hint
- ✅ 新增 `null_behavior` 处理数据缺失场景
- ✅ 新增 `sample_question` 作为 few-shot 示范
- ✅ `metric_name` 替代 `variable_name`（命名更清晰）

#### 3.2.3 改造 `geo_report_templates`

**不 DROP 重建**，改为 **ALTER 新增 `wizard_config` JSONB 列 + UPDATE 数据**（保持已有的 UUID 稳定，不破坏前端）：

**`wizard_config` schema 约定（content_generation 类型）**：
```jsonc
{
  "version": 1,
  "steps": {
    "content_goal":     {"enabled": true, "default_methodology_snippets": ["content_strategy_faq"]},
    "content_type":     {"enabled": true, "default": "faq"},
```

**两层 contract 的语义**：

| 层 | Analyzer 用 | Content 用 | 含义 |
|---|---|---|---|
| 数据层 | ✅ `required_metrics` | ✅ `required_metrics` | 必须计算/引用的 Analyzer 数据指标，都引用 `geo_analysis_metrics` |
| 交付层 | ✅ `required_chapters` | ❌ | Analyzer 必须出现的 H2 章节 |
| 质量层 | ❌ | ✅ `required_subgoals` | Content 必须覆盖的 RAFT 子目标，引用 `geo_optimization_subgoals` |

## 4. Phase 3 — Topic 语义化 + Auto-Discovery

### 4.1 目标
把 Topic 从"产品线"重定义为"话题 / 语义群"；Setup 阶段自动爬取客户官网抽取 Topics 和 Products。

### 4.2 Topic 语义化

**DB 变更**：`geo_client_topics` 表
```sql
ALTER TABLE geo_client_topics
    ADD COLUMN IF NOT EXISTS topic_type TEXT DEFAULT 'semantic_topic'
        CHECK (topic_type IN ('product_line','semantic_topic'));
-- 已有 Roborock 等客户数据 UPDATE 为 'semantic_topic'
```

**Agent NL2SQL schema 注释更新**：在 `geo_agent/src/tools/schema_hints.py` 里更新 Topic 的语义描述，让 Agent 知道 Topic 是话题而非产品线。

**前端**：Client Setup 页面 Topic 编辑组件加 `topic_type` 切换（产品线 vs 话题），UI 提示差异。

### 4.3 Auto-Discovery 4-Layer Fallback Crawler

**服务位置**：`geo_saas/src/routers/onboarding/auto_discovery.py`（**不放 geo_agent**，避免把 LangGraph 复杂度引入 setup 阶段；onboarding 是一次性、幂等的场景）

**端点**：
- `POST /api/onboarding/auto-discover` — 输入 `{brand_name, website_url}`，返回 `{topics: [], products: []}`

**4 层 Fallback**：
1. **Layer 1** — GET `/robots.txt` → 解析 `Sitemap:` URL → 拉 sitemap XML → 抽 URL 和标题
2. **Layer 2** — 尝试常见 sitemap 路径（`/sitemap.xml`, `/sitemap_index.xml`, `/sitemap_products.xml`）
3. **Layer 3** — GET 首页 HTML → cheerio 解析 `nav` / `header` 里的 `<a>` → 提取分类链接
4. **Layer 4** — 把 URL 列表 + 页面标题喂给 Gemini Flash → 抽 Topics 和 Products

**前端**：Setup 页面 "Tracking Strategy" 步骤新增 "Auto-Discover from Website" 按钮 + 结果预览 + 用户手动编辑

**已验证**：
- `www.roborock.com`（中文站）→ 无 robots.txt，需要 Layer 3/4
- `us.roborock.com`（Shopify）→ Layer 1 可用
- 参考：`project_auto_discovery_design.md`

- `migrations/028_phase3_auto_discovery.sql` — 如需 schema 变更（目前暂无，端点是无状态的）
