Cloud Scheduler 与 User Audit：当前真实调用链

Admin 是主要配置面，但 Scheduler 会直接回调 Admin、SaaS 或 Agent 的机器入口。

三类 Cloud Scheduler 任务

Workspace 数据作业
Admin UI配置 Workspace 的采集、分析、LLM Discovery cron
↓
Cloud Scheduler携带服务账号 OIDC
↓
Admin API 回调/api/clients/{client_id}/jobs/{job_type}/run
↓
Cloud Run JobCollector / Analyzer / LLM Discovery
SaaS 定时报表
SaaS 分析 UI保存分析任务并填写 cron
↓
Cloud Scheduler携带服务账号 OIDC
↓
SaaS API 回调/api/insights/analysis/runs/{task_id}/trigger_cron
↓
报表 Pipeline创建自动运行实例
Agent 定时任务
Admin Agent Tasks启用/停用已有 Agent task 的计划
↓
Cloud Scheduler携带服务账号 OIDC
↓
Agent API 回调/api/agent/tasks/{task_id}/trigger_cron
↓
Agent Pipeline按 task_type 执行 Analysis 或 Content

User Audit：现状与建议

当前：混合模式
页面访问React 路由监听器主动 POST audit event
大部分写操作fetchJSON 成功后 fire-and-forget POST audit event
少量 Admin 敏感操作业务 SQL 内联 INSERT 审计表
  • 原业务 Promise 不等待审计请求完成
  • 但每条审计都有额外 HTTP、鉴权和单行 INSERT
  • 直接 API / SSE / 非统一 fetch 调用可能漏记
  • action、route、status 主要由浏览器上报，可伪造
建议：服务端声明式切面
静态技术权限注册表同一条 route 声明 feature、capability、audit policy
统一 APIRoute / Dependency鉴权后取得 user、workspace、task_type 与规范化路由
中央 Audit Writer只记录有业务意义的动作，统一脱敏和 action_key
  • 权限与审计共用同一份路由元数据，避免重复维护
  • 页面浏览仍可保留前端 best-effort 统计
  • 机器任务标记 system identity，不套 Workspace 用户 RBAC
  • 请求体不做通用全量保存，只允许白名单元数据解析器
“不阻塞”与“绝不丢审计”不能同时免费获得：进程内异步队列最快，但实例退出时可能丢少量事件；同步数据库写最可靠，但会增加一次写入延迟；可靠异步需要 Pub/Sub / outbox 等持久化缓冲。
下一项需要确认

User Audit 是产品运营级行为记录（允许极少量丢失），还是合规/安全级审计（要求不可伪造、尽量不丢）？这个选择决定写入链路是否需要可靠消息或事务 outbox。
